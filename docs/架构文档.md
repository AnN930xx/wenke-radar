## 1. 项目定位

### 1.1 一句话定位

**面向非技术/泛商业方向求职者的官方岗位增量雷达**：每天定时抓取 39 个招聘源官方 API，
按求职画像过滤出对口岗位，用可投程度评分排序，只报「今日新增」，微信推送到手机。
Fork 仓库、改一份配置、加一个 Secret 即可运行，零服务器、零运维、零费用。

### 1.2 解决什么问题

- 招聘信息分散在几十个官网/小程序/ATS 平台，逐个刷不现实；
- 聚合平台滞后、不全、夹广告；BOSS/智联等要登录且反爬极强，不合规不可持续；
- 求职者真正需要的是「**今天新放出了哪些我能投的岗，哪些最值得投**」——增量 + 排序信号。

### 1.3 差异化

1. **官方接口直连为主**：37/39 源走各公司官网/ATS 的真实 API（含响应解密、动态令牌、form 编码老站），
   非二手聚合；余 2 个猎聘源属**聚合发现层**（AGGREGATOR_DISCOVERY），仅作线索补充，不负责岗位关闭/更新时间/真实性判断（来源分级见附录 A）；
2. **增量哲学**：「每日新增」是第一公民，存量只留计数——为"人每天看一眼"设计；
3. **画像过滤 + 可投评分**：方向 × 城市 × 届别 × 排实习 × 社招排资深；再按方向强度/应届友好/新鲜度评分排序；
4. **配置与引擎分离**：方向、城市、届别、经验阈值全部配置化，用户改配置不碰引擎、改坏也不影响抓取；
5. **低成本接新源**：5 套 ATS 平台基类 + 配置驱动的 GenericScraper，同平台新公司几行配置接入；
6. **全免费基建**：GitHub Actions（调度+算力）+ Actions Cache/artifact（数据接力+兜底）+ git（归档）+ Server酱（推送）。

### 1.4 双仓结构（v3.0 新增）

| 仓库 | 定位 | 画像 |
|------|------|------|
| 上游私有自用仓 | 自用生产环境 + 完整开发文档/踩坑/工作日志 | 窄画像（定制画像） |
| `wenke-radar`（开源，MIT） | 通用引擎，供任何人 Fork | 全谱系默认画像（11 方向），个人数据零残留 |

引擎改进在两仓间同步；开源仓从首个提交起 git 历史干净，无任何真实个人数据。

## 2. 技术选型与技术栈

| 层面 | 选型 | 选择理由 |
|------|------|---------|
| 语言 | Python 3.11 | 抓取/解析/SQLite 生态成熟；单人可维护 |
| HTTP | `requests` + `urllib3.Retry` | 轻量；统一 Session 连接复用；5xx 自动重试（backoff 递增） |
| HTML 解析 | `beautifulsoup4` | 仅 SSR 表格页/猎聘页需要；主力是 JSON API，不引入浏览器 |
| 解密 | `pycryptodome`（AES-CBC） | Moka 平台响应加密，逆向后本地解密（见 §7.1） |
| 存储 | SQLite（标准库 `sqlite3`） | 单文件零部署；两库分离（可再生抓取数据 / 人工投递数据） |
| Excel | `openpyxl` | 投递追踪表导出（状态配色、统计看板） |
| 调度/算力 | GitHub Actions（双 cron + workflow_dispatch） | 免费免服务器；cache 加速 + artifact 快照兜底；concurrency 防并发分叉 |
| 测试 | pytest + fixture 录制回放 + GitHub Actions CI | 150 单测锁业务规则；31 源真实响应样本离线测解析契约 |
| 推送 | Server酱（微信）/ 企业微信机器人 | 免费无需 App；环境变量注入，多 key 支持 |
| **刻意不用** | 浏览器自动化 / 爬虫框架 / Web 框架 / ORM | 真实 API 足够；依赖越少云端越快越稳（全量 39 源约 9 分钟） |

依赖总数 **5 个第三方包**（requests / bs4 / pycryptodome / openpyxl / lxml），无框架绑定。

## 3. 系统总览与数据流

### 3.1 运行时全景

```
             ┌──────────────────────────────────────────────────────┐
每天 09:00 ─►│  GitHub Actions (daily.yml)                          │
 +10:00 备份 │  ① cache restore jobs.db（miss 则 artifact 快照兜底）   │
 (北京时间)   │  ② 定时去重守卫（当天已出报告则跳过）  ③ python main.py │
             │  ④ cache save + 上传 artifact  ⑤ commit reports/ 归档  │
             └───────────────────────┬──────────────────────────────┘
                                     │
             ┌───────────────────────▼──────────────────────────────┐
             │  main.py（编排层）                                    │
 39 个招聘源 ─►│  scrapers/*  ─► [FetchResult 完整性判定] ─► store     │
 (官方 API)   │  (List[JobItem])                        (入库/对比/  │
             │        │                                  归档/事件)  │
             │        ▼                                     │        │
             │  filters（画像过滤）─► scoring（可投评分）─────┤        │
             │                                     ┌────────┴──────┐ │
             │                                     ▼               ▼ │
             │              report.generate_brief      generate_push_brief
             │              (完整日报→reports/留档)   (⭐评分精简版→push→微信)│
             └───────────────────────────────────────────────────────┘
```

### 3.2 一次运行的完整数据流

1. **抓取**：`main.run_all_scrapers()` 遍历 `SCRAPERS` + `GENERIC_SOURCES`，每源 `fetch()` 返回
   `List[JobItem]`；单源异常逐源 try/except 兜住记 0 条继续，同时产出 `FetchResult` 完整性元数据。
2. **完整性判定**：对账"分页原始条数 vs 服务端报告总数"，`complete=False` 的源列入 suspects。
3. **入库+新增对比**：`store.save_jobs()` 以 `(company, job_id)` 主键 upsert；首见岗位记 `first_seen`
   并加入 `new_keys`（=「今日新增」）；suspects 源本次跳过归档（没抓全 ≠ 岗位下线了）。
4. **自动归档 + 事件流**：本次未抓到的旧岗挪入 `jobs_archive`；全程记 `job_events`
   （CREATED/BOOTSTRAP/REOPENED/UPDATED/CLOSED）。
5. **过滤 + enrichment**：`filters.filter_jobs()` 先对每个岗位 `enrich()`（从 JD 正文解析经验年限等结构化字段），
   再裁出对口子集：校招走 届别+排实习，社招豁免这两项、改走 排资深（含 JD 经验），共用 方向+城市。
6. **评分**：`scoring.score_job()` 给对口岗打 0-100 分（方向强度/城市/应届友好/经验门槛/新鲜度）。
7. **双渲染**：完整日报写 `reports/` 留档；精简推送版按公司分组、公司内高分在前、≥85 标 ⭐。
8. **推送**：Server酱多 key 逐个投递 + 企业微信；逐渠道 try/except，失败仅记录不抛出。

## 4. 代码架构

### 4.1 分层结构与依赖规则（架构不变量）

```
config.py         纯配置数据（画像/源开关/守卫阈值/各公司参数），无逻辑
user_profile.py   用户自定义方向隔离区（MY_DIRECTIONS，坏配置安全忽略、不影响引擎）
   ↓
domain/           领域层：models.JobItem(数据契约) + classify(类别推断)
                  + enrich(JD正文→经验年限抽取) + results.FetchResult(完整性元数据)
   ↓
scrapers/         抓取层：BaseScraper + 5 平台基类 + 39 源（re-export JobItem 兼容）
   ↓
filters.py        过滤层：画像规则纯函数（方向/城市/届别/排实习/排资深）+ 届别通用推导
scoring.py        评分层：可投程度 0-100（过滤答"能不能投"，评分答"多值得投"）
   ↓
store.py          存储层：jobs.db 读写/新增对比/归档/四道守卫/source_health/job_events
   ↓
report.py         渲染层（不直连 DB）      tracker.py  投递记录层（applications.db 唯一入口）
push.py           推送层（读环境变量，多 key）
   ↓
main.py           编排层（流程串联 + FetchResult 完整性判定，无业务细节）
```

**规则：依赖只向上，禁止反向与环形。** import 关系审计（2026-07-24 复核）：

| 模块 | imports（项目内） | 验证 |
|------|------------------|------|
| config.py | 无（运行期惰性读 user_profile，失败安全回退） | ✅ 纯数据 |
| user_profile.py | 无 | ✅ 纯数据，与引擎完全解耦 |
| domain/* | config | ✅ 领域层不依赖任何实现层 |
| scrapers/*.py | domain, config | ✅ 不碰 filters/store/report；**且不依赖 KEYWORDS**（AST 测试保证） |
| filters.py | domain, config | ✅ 纯函数，无 IO |
| scoring.py | config | ✅ 纯函数 |
| store.py | domain, filters, config | ✅ 届别解析复用过滤层 |
| report.py | domain, filters, scoring, config, tracker(惰性) | ✅ 不直连任何 DB |
| tracker.py / push.py | 仅标准库 + openpyxl/requests | ✅ 完全自治 |
| main.py | 以上全部 | ✅ 唯一"知道全局"的模块 |

**分层动机**：变更频率不同——网站接口经常变（抓取层）、求职偏好偶尔调（过滤/评分层）、
日报样式偶尔改（渲染层）、用户加方向随时（隔离区）。分层后各自独立演化，互不牵动。

### 4.2 统一数据模型

`JobItem`（dataclass）是全系统的通用货币：
```
company / job_id / title / category / location / url / publish_time / tags
recruit_type("校招"|"社招") / description(JD正文,瞬态不落库) / experience_min_years(enrich解析,瞬态)
dedup_key = f"{company}::{job_id}"     ← 全局去重键，要求 job_id 在公司内稳定
```
39 个异构源在抓取层内部各自消化差异，出了抓取层全是同构 JobItem——下游对"数据从哪来"零感知。

### 4.3 存储设计

**两个 SQLite 库，性质不同，物理分开：**

| | `data/jobs.db`（抓取库） | `data/applications.db`（投递库） |
|---|---|---|
| 内容 | jobs / jobs_archive / **job_events** / **source_health** / v_job_summary | applications（投递状态流转） |
| 性质 | 机器数据，**可再生** | 人工数据，**不可再生** |
| 持久化 | 不进 git；Actions cache 接力 + artifact 快照兜底 | 进 git |
| 唯一写入方 | store.py | tracker.py |

关键设计：主键 upsert 幂等；归档按 **job_id 集合对比**而非时间戳（跨端时区不可比）；
老库启动自动 `ALTER TABLE` 补列，幂等迁移。

### 4.4 抓取器三级复用体系

1. **平台基类**（一次逆向，多家复用）：FeishuAts（飞书×5）/ Beisen（北森×6）/ Baiku+Yili（百库×3）/
   Moka（×2）/ LiepinCompany（猎聘×2）——接同平台新公司只需子类 + config；
2. **独立抓取器**：大厂自研接口一司一模块（×21）；
3. **GenericScraper**：纯配置声明零代码接入标准 JSON 接口——社区贡献新源的主通道。

校招/社招同司复用：社招抓取器一律是校招类的子类，只改类属性。

### 4.5 领域逻辑三件套（v3.0 重点）

- **enrichment（`domain/enrich.py`）**：抓取层只负责把 JD 正文带回 `description`，
  经验年限的解析与判断在此层做（外部审查"经验判断不该在抓取期"的修复）。
  好处：同一份抓取数据可复用给不同经验阈值的用户画像，无需重抓。
- **评分（`scoring.py`）**：过滤是二值（能不能投），评分是多值（0-100，多值得投）。
  权重是经验参数，按真实反馈调；推送用它排序 + ⭐ 高匹配标记。
- **届别通用化（`filters.py`）**：`TARGET_GRAD_YEARS` 填任意年份组合（[2024]、[2027,2028]、
  跨十年都行），匹配 token 与排除窗口全部自动推导，运行期改配置即刻生效，非法值人话报错。
  `parse_recruit_year` 识别 20xx 全部年份，不锁定某个年代。

### 4.6 用户配置隔离区（v3.0 新增）

`user_profile.py` 是"用户区"与"引擎区"的边界：
- 用户在 `MY_DIRECTIONS` 加方向 → `config.apply_user_directions()` 合并进 KEYWORDS；
- 对任何非法输入（非 dict / 值非 list / 空名 / 非字符串）安全跳过、绝不抛异常；
- 文件不存在=静默用内置；语法错=提示并回退，每日任务不崩；
- **隔离性硬证据**：AST 测试扫描全部抓取器，确认无一读取 KEYWORDS——所以改方向绝不影响"抓什么"
  （抓取器永远抓全量，方向只决定"展示哪些"）。

### 4.7 渲染与推送

- **双产物分离**：`generate_brief()` 完整日报（留档）与 `generate_push_brief()` 精简推送（给人看）
  是两个独立函数；推送格式有独立规范文档，先改文档再改代码；
- 渲染层不直连 DB（投递数据经 tracker 取，try/except 包裹）；
- 推送层按渠道/按 key 独立投递，全部失败也不抛出（推送是加急通道，reports/ 落盘才是保底）。

## 5. 部署与运维设计

- **触发**：cron 每天北京 09:00 主触发 + 10:00 备份触发（抗 GitHub cron 延迟/丢弃）
  + workflow_dispatch 手动；定时去重守卫保证多触发点不重复推送（当天已出报告则跳过）；
- **数据接力**：cache key 带 `run_id`（永远精确未命中）→ 走 restore-keys 前缀匹配拿最近的库；
  cache 未命中时从最近一次运行的 artifact 快照（90 天保留）恢复——去掉 cache 单点；
- **首次自举**：库不存在自动切 `--full` 全量初始化；
- **并发防护**：workflow `concurrency` 组串行化，杜绝定时/手动并发写出分叉状态；
- **归档提交防撞**：push 前 `pull --rebase --autostash` + 3 次重试；
- **步骤级容错**：cache save / 导出 / 摘要 / 提交步骤全 `if: always()`；
- **秘钥管理**：推送 key 走 GitHub Secrets，日志显示 `***`。

## 6. 独立性与容错审查 ⭐

> 结论：**成立**。方法：代码走查 + 故障注入推演 + 压测实证。

### 6.1 故障影响面总表

| 故障场景 | 实际影响 | 隔离机制 |
|---------|---------|---------|
| 某抓取器抛异常 | 该源记 0 条，其余 38 源照常 | main 逐源 try/except |
| 某源官网关闭 | 优雅返回空列表，**不触发归档** | store 空集合守卫 |
| 分页静默断裂（只抓到部分） | 完整性对账判 suspect → 跳归档 + 日报告警 + 健康表记录 | FetchResult 协议 |
| 新接入源存量灌入 | ≥5 岗静默入库不计新增 | store bootstrap 守卫 |
| 归档量骤降（疑似部分抓取） | 要归档 >50% 库存则跳过并告警 | store 骤降守卫 |
| 反爬源数量抖动（猎聘） | 不归档不误报 | config `no_archive` 豁免 |
| **用户方向配置写坏** | 忽略自定义、回退内置方向，引擎照跑 | config.apply_user_directions 全类型校验 |
| 投递库损坏/缺失 | 日报少一段投递概览，主体完整 | report 整段 try/except |
| 推送渠道/某 key 故障 | 打印失败原因，运行继续成功退出 | push 逐渠道逐 key try/except |
| Actions 步骤失败 | 数据库仍 cache save，产物仍提交 | daily.yml 各步 `if: always()` |
| jobs.db 丢失 | cache miss → artifact 快照恢复；再无则 `--full` 重建 | 快照兜底 + 自举分支 |
| 单条岗位字段畸形 | 逐字段兜底，坏一条不坏一批 | 各 _parse + helper |

### 6.2 抓取器之间的独立性

控制流独立（逐源 try/except，异常边界=源边界，无共享可变状态）；数据独立（store 按 company
分组归档，SQL 均带 `WHERE company=?`）；唯一共享资源 HTTP Session 经压测两种模式（独立/并发）
验证无干扰；注册即隔离（新源只在 SCRAPERS 加一行）。

### 6.3 层间独立性

抓取层换实现下游零改动（清洁重写 11 文件抓取量逐源一致为证）；过滤/评分/渲染/推送各层可单独替换；
**用户配置层与引擎彻底解耦**（AST 证抓取器不依赖方向词表）。

### 6.4 已知的刻意取舍

| 取舍 | 理由 |
|------|------|
| 顺序抓取而非并发 | 每日一次场景 9 分钟够用；并发放大反爬风险且引入共享限流状态 |
| 完整性对账阈值是经验参数 | 服务端总数 ≠ 可抓总数（北森 Count 虚高，#28）；全局 0.9 + 按源 complete_ratio 校准 |
| 每日新增语义 = first_seen | 各源发布时间字段缺失/格式乱，first_seen 跨源统一且与发布日实测基本一致 |
| 骤降守卫无状态 | 真实缩招 >50% 会持续跳归档（日志可见）；跨源去重/内容指纹在阶段二收尾后可进一步根治 |

## 7. 项目难点与解决方案 ⭐

> 按"难度 × 通用价值"排序。完整 28 条见 docs/错误日志.md。

**7.1 Moka 响应加密**：密文 `{data, necromancer}`，AES-CBC，key=每次下发的 necromancer、
IV=固定常量，封装进 `MokaScraper` 基类。
**7.2 京东社招 form 编码老站**：传 JSON 被静默忽略，浏览器 hook fetch 抓真实 body 才破解。
**7.3 伊利百库旧版动态令牌**：先 GET 页面正则提取 operational 令牌再调接口。
**7.4 飞书 ATS 多形态参数化**：一套引擎五种用法，差异收进 4 个类属性。
**7.5 社招资深岗识别**：JD 正文经验年限三组正则（区间取下限、防年份误匹配、中文数字），
v3.0 已从抓取期上收到 enrichment 层。
**7.6 跨端时区陷阱**：归档判据改用时区无关的 job_id 集合差集。
**7.7 无状态 CI 上的有状态增量**：cache key 带 run_id 强制走前缀匹配实现"链式接力"。
**7.8 反爬对抗的分寸**：能绕的补指纹头/限速，硬壁垒（登录/签名）探明即放弃并记录；只调公开接口。
**7.9 北森 pageSize 越大返回越少 + Count 虚高**：per-company page_size + complete_ratio 校准。
**7.10 增量语义正确性**：job_id 取平台原生稳定 id + 主键幂等 + 抓取量逐源回归。
**7.11（v3.0 新增）配置通用化不崩盘**：届别任意年份自动推导 + 非法值 fail-fast 报错；
用户方向隔离区对坏输入全类型校验——"用户随便改配置也不搞坏引擎"有测试背书。

## 10. 审查结论

1. **架构**：**分层基本完成**、依赖只向上无环形；数据契约统一，两库按性质分离；用户配置层与引擎解耦。
   诚实说明：仍有 domain→config、store→filters、report→tracker 的向上依赖，config.py 混配置与合并逻辑，
   这些是"基本分层"而非"完全解耦"，精修计划见 §9.4。
2. **独立性**：抓取器控制流/数据/状态三重独立；层间可单独替换；用户配置层与引擎解耦有 AST 背书。
3. **容错**：故障影响面表覆盖 12 类场景均有隔离机制，最坏情况"当日数据不全"，无单点崩溃/数据损坏路径。
4. **数据可信**：两轮审查的 P0/P1 结构待办已全部工程落地并逐项生产验证——来源身份、FetchResult
   唯一返回、内容指纹、归档状态机（生产环境当场归档了被旧 50% 阈值永久卡住的滞留岗位）。
5. **可维护性**：179 测试 + 31 源契约 + AST 分层不变量 + CI，任何核心改动都有测试兜底。
6. **短板如实陈述**：跨源去重未做（同岗位可能多源重复推送，canonical_job_id 地基已铺）；
   用户反馈闭环缺失（评分权重靠人工调）；config.py 拆分暂缓（P2 非阻塞）；
   来源偏互联网大厂+快消，文科垂直机构覆盖尚薄。

**综合评价：作为个人自用系统已成熟可长期运行；作为开源个人工具具备发布条件，但补完 `source_id`
再公开更稳。不转向大招聘平台爬虫（合规红线），继续经 ATS 基类 + 行业公司名单扩大官方源覆盖。**
